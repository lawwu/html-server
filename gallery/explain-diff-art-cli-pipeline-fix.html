The error that happened twice: why art rm printed a Python traceback

A four-line helper, fmt(), and the small fact about shell pipelines that made it necessary.

Suppose you ask the artifact server to trash a page that doesn't exist. The server answers, quite reasonably, with an HTTP 404 and a one-line JSON error. The art command-line tool dutifully prints that error. And then, a heartbeat later, it prints fifteen lines of Python traceback ending in JSONDecodeError. Nothing is actually broken twice — but it looks as if it were, and the useful line is buried under the noise.

This page explains why that happened and why the fix is a small function that does nothing more exotic than waiting.

Part 1Background: pipelines, subshells and set -e

If you already know that each stage of a bash pipeline runs in its own subshell, skip to Part 2.

When you write a | b in bash, the shell starts both commands at once and connects a's standard output to b's standard input. Neither waits for the other to finish before starting. Crucially, when a or b is a shell function rather than an external program, bash runs it in a subshell: a forked copy of the current shell, with its own process and its own fate.

Definition · subshellA child process that starts as a copy of the parent shell — same variables, same functions — but whose exit ends only itself. The parent learns about it only through an exit status.

That last point matters for scripts written in the defensive style. art begins with set -euo pipefail, which means:

  • -e — exit as soon as a command fails;
  • -u — treat an unset variable as an error;
  • -o pipefail — a pipeline fails if any stage fails, not just the last.

These are excellent defaults, but they all act after a pipeline has finished. pipefail decides what the pipeline's exit status is; it cannot reach back in time and stop the other stage from running.

The narrower context: exit inside a function inside a pipe

Here is the whole bug in miniature. Paste it into a terminal:

set -euo pipefail
fail() { echo "fail: giving up" >&2; exit 1; }
fail | python3 -c 'import json,sys; json.load(sys.stdin)'
echo "never printed"

You will see both the message and a traceback. fail's exit 1 ends only the left-hand subshell. Its stdout closes, empty. Python, already running on the right, reads zero bytes and asks json.load to parse them, which raises. Only then does the pipeline finish, pipefail reports failure, and -e stops the script — so the final echo really is never printed. The script fails correctly; it just fails noisily.

Part 2Context: how art talks to the server

art is a thin bash wrapper around curl. Every request goes through one function, call, which runs curl, splits off the HTTP status code that -w '\n%{http_code}' appends, and on any status of 400 or above calls die with the server's JSON error field:

call() {
  local out code
  out="$(curl -s -w '\n%{http_code}' "$@")" || die "can't reach $A (is the server running?)"
  code="${out##*$'\n'}"; out="${out%$'\n'*}"
  if [[ "$code" -ge 400 ]]; then
    die "$(python3 -c '... print(json.loads(sys.argv[1])["error"])' "$out" ...)"
  fi
  printf '%s\n' "$out"
}
die() { echo "art: $*" >&2; exit 1; }

On success, call prints the JSON body. Most subcommands then want something friendlier than raw JSON — a one-line-per-page listing for art ls, a "published v3: …" line for art put — so each pipes call's output into a small Python formatter. And there it is: die is an exit, and call was on the left of a pipe.

Key ideaA function that "dies" is only as fatal as the process it runs in. Put it on the left of a pipe and it kills a subshell, not the script.

Part 3Intuition: two processes, one exit

Let's follow a concrete request — art rm missing-page.html — through the old code. The server returns 404 with body {"error": "no artifact named 'missing-page.html'"}.

HTTP 404 {"error":"no artifact named 'missing-page.html'"}
body + status→

call (subshell A)

code=404 ≥ 400 die → stderr: "art: no artifact…" exit 1 stdout: ""

0 bytes→

$ art rm missing-page.html art: no artifact named 'missing-page.html' Traceback (most recent call last): File "<string>", line 1, in <module> … json.decoder.JSONDecodeError: Expecting value: line 1 column 1 (char 0)
Both stages run at once. A's exit cannot stop B; it only starves it. (Error text is illustrative.)

The fix changes the shape of the computation, not any one line of it. Instead of streaming, it does the two steps in sequence and checks the first before starting the second:

After · fmt FORMATTER call …
Error path
json="$(call …)"die → exit 1assignment fails → set -e exitsformatter
Success path
json="$(call …)"status 0, json='[{…}]'printf '%s\n' "$json" | formatter
$ art rm missing-page.html art: no artifact named 'missing-page.html' $ echo $? 1
Command substitution waits for call to finish, so its exit status is known before anything reads its output.

Command substitution — $( … ) — also runs its contents in a subshell, so die still only exits a child. The difference is that the parent is now waiting on that child, and the assignment json="$(…)" takes the child's exit status as its own. Under set -e, a failing assignment ends the script on the spot, before any formatter is started.

Streaming (pipe)Producer and consumer overlap. Great for large outputs; failure in the producer is reported only after the consumer has seen whatever was — or wasn't — produced.
Capture, then formatProducer finishes first; its status gates the consumer. Costs memory proportional to the output — trivial for a JSON API response.

Part 4The code, change by change

1 · A new helper, fmt

The heart of the change is one function and the comment explaining why it exists:

# Run a request to completion before formatting it: in "call | formatter" a failed# call would only exit the pipe's subshell, and the formatter would choke on nothing.fmt() { local json; json="$("${@:2}")"; printf '%s\n' "$json" | $1; }

Read it as "fmt FORMATTER COMMAND ARGS…". $1 is the formatter; "${@:2}" is everything after it, which is run as a command, quoting preserved. Its output is held in json; only if that succeeded does the formatter get to read it.

Edge case · why local json; is its own statementIt would be tempting to write local json="$(…)". Don't: local is itself a command, and its exit status (0, it declared a variable) replaces the substitution's. set -e would never see the failure, and you'd be back to formatting an empty string. Splitting declaration from assignment is what makes the whole fix work.

2 · Formatters become named functions

The JSON-to-text programs used to sit inline on the right of each pipe. They are now small functions so they can be passed by name as fmt's first argument:

summary() { python3 -c "$SUMMARY_PY"; }  # inside the put branch:    put_fmt() { A="$A" python3 -c "$PUT_PY"; }

Passing a name rather than a string avoids having to eval anything, and functions defined inside a case branch can close over that branch's variables — restore_fmt captures the version number n it is about to report.

3 · Every call … | formatter becomes fmt formatter call …

The remaining hunks are mechanical. The before lines below are reconstructed from the description of the bug (the original wasn't committed); the after lines are the file as it stands.

-  ls)   with_auth "$A/api/artifacts?limit=500" | summary ;;+  ls)   fmt summary with_auth "$A/api/artifacts?limit=500" ;;
-  find) … with_auth "$A/api/artifacts?q=$(enc "$*")" | summary ;;+  find) … fmt summary with_auth "$A/api/artifacts?q=$(enc "$*")" ;;
-    call -X PUT --data-binary "@$file" … "$A/api/artifacts/$(enc "$name")" \-      | A="$A" python3 -c "$PUT_PY" ;;+    fmt put_fmt call -X PUT --data-binary "@$file" … "$A/api/artifacts/$(enc "$name")" ;;
-    call -X POST … "/versions/$2/restore" | N="$2" python3 -c '…' ;;+    fmt restore_fmt call -X POST … "/versions/$2/restore" ;;

Notice what didn't change: art diff and art views print the server's response directly with no formatter, so they never had the bug and still call with_auth bare.

Why not just check PIPESTATUS?You could inspect ${PIPESTATUS[0]} after the pipe, but by then the formatter has already run and printed its traceback. The point is to not start the consumer at all, which needs the producer to finish first.
