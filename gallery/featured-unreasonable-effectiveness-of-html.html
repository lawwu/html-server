An argument for a small change in habit: when you ask Claude Code for a plan, a spec, a review or a report, ask for an HTML file instead of Markdown. The output gets richer, people actually read it, and you stay closer to the decisions the agent is making.

The argument, in six moves

Paraphrased; read the original for the examples and screenshots.

Long Markdown goes unread

Past a hundred or so lines, neither the author nor colleagues really read a Markdown plan. It is also a poor carrier for color, layout or diagrams, and awkward to pass around.

Nobody hand-edits these files now

Markdown's great virtue was being easy to edit by hand. When Claude drafts and revises the plan, that virtue matters much less.

HTML carries more

Tables, styled design samples, SVG figures, code, controls, spatial layouts and images all fit naturally — no more ASCII boxes or emoji standing in for colors.

It is easier to read and to share

Navigation, tabs and responsive layout make long documents tractable, and a link opens in any browser, so the thing actually gets looked at.

It talks back

Sliders, toggles and "copy as prompt" buttons let the reader tune a choice and hand the result straight back to the agent.

Worth the extra tokens

HTML costs more to generate than Markdown. With large context windows, the author judges the gain in quality and readership worth it — and you can start with nothing more than "make an HTML file."

“I feel more in the loop now than I ever did before.”— Thariq Shihipar, on reading HTML plans instead of skimming Markdown

What to ask for

The kinds of HTML artifact the essay describes, and where this gallery has a worked example.

specs & planning

Exploration and option comparison

Several approaches side by side as cards, each with code and trade-offs; layout variants in a grid; implementation plans with mockups and data-flow diagrams.

example → artifact-server-architecture
code review

PR explainers and annotated reviews

A change explained for a reviewer, or a rendered diff with margin notes tagged by severity: blocking, nit, nice-to-have.

examples → explain-diff · pr-review
understanding

Explainers and diagrams

A navigable page on how a subsystem works — contents, a TL;DR, collapsible steps, SVG flowcharts and state diagrams.

example → lifecycle state machine
design & prototypes

Tokens, components, animation tuners

Swatches and type scales rendered for real, components in every variant, and sliders for tuning an animation with a button to copy the chosen values.

example → easing-curve-tuner
reports & learning

Reports and interactive explainers

Status and incident reports, feature summaries, and teaching pages where the reader can poke at the idea.

examples → gradient descent · birthday paradox
custom editors

Throwaway single-purpose tools

A drag-to-prioritise ticket board, a feature-flag editor, a dataset curation or annotation tool, value pickers — each with an export button that hands the result back.

example → ticket-triage-board

Short version: the next time you would ask for a Markdown plan, ask for an HTML file — and open it.
