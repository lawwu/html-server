Open questions

Not decided, and not decided here. Each names an owner and the phase it blocks; the notes are what the docs say, not an answer.

  • Q1

    Keep auto mode as the starting mode, and require the sandbox?

    With Claude Code v2.1.283 or later, terminal and VS Code sessions start in auto mode, which Team plans allow by default; permissions.disableAutoMode: "disable" turns it off. The docs say auto mode cuts prompts but doesn’t guarantee safety. The sandbox is off by default, runs on macOS, Linux and WSL2 but not native Windows, and needs bubblewrap and socat on Linux.

    OwnerSecurity engineerBlocksP3EvidenceP1 sandbox logFromS11

  • Q2

    Which credential pays for CI?

    For a secret shared across repositories, the docs recommend a Claude Console API key over an OAuth token, which is tied to the subscription of whoever generated it; workload identity federation avoids storing a long-lived key at all. Both bill per token, outside the seat allowance; an OAuth token would draw on its owner’s subscription instead. A Console key belongs to a separate organization, so P3’s policy doesn’t reach those runs.

    OwnerDirector of engineering with finance partnerBlocksP5FromS12

  • Q3

    Also deliver the policy through MDM on the Macs?

    The docs call endpoint-managed settings the stronger option on MDM-enrolled devices, and say login restrictions (forceLoginMethod, forceLoginOrgUUID) have to come from device management, because server-managed settings only arrive after someone signs in to the organization. When both deliver a policy, Claude Code uses the server-managed one by default. The Linux desktops would stay on server-managed settings.

    OwnerSecurity engineer with ITBlocksnothing; revisit after P3FromS13 R4

  • Q4

    Standard or Premium seats, and turn on usage credits?

    Each seat’s allowance depends on its tier, is shared with Claude chat, and resets on a rolling five-hour window and a weekly window. Usage credits let people keep working past it, under spend limits set for the organization, a group or a member. Raised by the docs, not the brief.

    OwnerPlatform lead with finance partnerBlocksinviting the other 35 (P3)EvidenceP1 limit logFromdocs, S1

  • Q5

    Add OpenTelemetry export?

    The spend report updates daily. OpenTelemetry streams per-user tokens and estimated cost to our own stack in near real time, which allows alerts on spikes, but with a claude.ai sign-in it carries user.email. Repo settings files can’t turn it on, so it would go in the managed policy.

    OwnerPlatform leadBlocksnothingFromS7 S8 S9

  • Q6

    Accept the Claude GitHub App’s permission set?

    The app has one permission set for every Claude feature that uses GitHub, and GitHub doesn’t allow accepting part of it. A custom app with only Contents, Issues and Pull requests covers the Action alone; the contribution metrics in P6 need the official app. Raised by the docs, not the brief.

    OwnerSecurity engineerBlocksP5Fromdocs

P1

Pilot with five volunteers

Learn what the team needs before anyone else gets a seat, and take the usage baseline the cost docs recommend measuring with a small pilot first.

Steps

  1. Invite the five from the admin dashboard. Each installs with the native installer, which updates itself in the background, and signs in with the claude.ai account the admin invited.
  2. Before the first session, each volunteer adds the S4 rules to ~/.claude/settings.json: deny rules for Read(./.env), Read(./.env.*) and Read(./secrets/**), plus permissions.disableBypassPermissionsMode: "disable". The docs note both work from a user’s own settings; P3 makes them policy.
  3. Work as usual for two weeks on product defaults. On v2.1.283 or later, terminal and VS Code sessions start in auto mode, where a classifier reviews actions instead of prompting.
  4. In week two, one macOS and one Linux volunteer turn on /sandbox and log what it breaks. Evidence for Q1.
  5. Everyone keeps a short log: any session or weekly limit message (Q4); commands approved with “Yes, and don’t ask again”, which Claude Code saves to .claude/settings.local.json (P2’s allow list); MCP servers connected, from /mcp (P4’s inventory); anything odd, reported with /feedback.
  6. Each volunteer drafts a CLAUDE.md for their repo with /init and keeps it on a branch until P2.

Acceptance checks

  • C1All five run claude doctor on day one and it reports no errors.
  • C2The analytics dashboard at claude.ai/analytics/claude-code shows daily active users and sessions for all five across the two weeks. That is the baseline.
  • C3Write-up delivered: allow-rule candidates, CLAUDE.md drafts, MCP inventory, sandbox breakages, limit messages.
  • C4The security engineer has read it, and Q1 and Q4 have the evidence they asked for.

RollbackTake Claude Code access off the five seats in the admin console. Nothing shared changed during the pilot, so nobody else notices.

P2

Shared project settings and CLAUDE.md

Owner

Steps

  1. The platform lead turns the pilot’s allow-rule candidates into a template .claude/settings.json: permissions.allow for each repo’s own build, test and lint commands, plus the S4 deny rules so they hold before P3 lands.
  2. Each tech lead opens a PR with .claude/settings.json and a CLAUDE.md, starting from the pilot draft or /init. It goes through normal review.
  3. Keep each CLAUDE.md under 200 lines, the docs’ target, with checkable instructions: build and test commands, conventions, layout. Personal preferences go in CLAUDE.local.md or ~/.claude/CLAUDE.md.
  4. Tell engineers two things from the docs: committed allow rules apply only after each person accepts the workspace trust dialog, while deny and ask rules apply at once; and CLAUDE.md is guidance Claude reads, not enforcement. Enforcement lives in settings.

Acceptance checks

  • C1Every active repo has both files, merged through a reviewed PR.
  • C2In a fresh clone, after accepting the trust dialog, /permissions lists the project rules with .claude/settings.json as their source.
  • C3/context all lists the repo’s CLAUDE.md under Memory files.
  • C4No shared CLAUDE.md runs over 200 lines, and git tracks no .claude/settings.local.json or CLAUDE.local.md.

RollbackRevert the PR. Claude Code watches settings files and reloads them in running sessions; personal overrides in .claude/settings.local.json are untouched.

Steps

  1. Write the policy below and add whatever Q1 decides: permissions.disableAutoMode, a sandbox block, or neither. The security engineer signs off.
  2. Leave allowManagedPermissionRulesOnly unset: it would make Claude Code ignore the repo rules from P2. Leave DISABLE_TELEMETRY unset too: it stops the data behind the analytics dashboard P6 reads.

Steps

  1. Security reviews the issue-tracker and docs-search servers. The docs say Anthropic doesn’t security-audit MCP servers, and that servers fetching external content add prompt-injection risk.
  2. Add the keys below to the P3 policy. managedMcpServers hands both servers to every user; the allowlist repeats their URLs so a hand-added copy is admitted too; allowManagedMcpServersOnly stops anyone widening it. Match by URL: a serverName entry isn’t a security control.

Risks and mitigations

The three risks named in S9, plus two the docs raise. No likelihood scores: the brief gives no basis for them.

RiskMitigationsOwner · from
R1 · Secrets reach prompts, transcripts or logs
  • Deny rules for .env, .env.* and secrets/ from day one: user settings in P1, repo files in P2, policy in P3, the workflow in P5.
  • Deny rules cover Claude’s file tools and commands that name the file, not grep -r over a folder or a script that opens files. The sandbox closes that gap at the OS level (Q1).
  • .claudeignore has no effect; move any entries into Read deny rules.
  • OpenTelemetry collects no prompt text or tool arguments unless OTEL_LOG_USER_PROMPTS or OTEL_LOG_TOOL_DETAILS is set; keep both off (Q5).
  • Transcripts sit in plaintext under ~/.claude/projects/ for 30 days by default; cleanupPeriodDays shortens that.
Security engineer · S4 S9
R2 · Prompt injection through issues, PR comments, web pages or MCP results
  • Approved MCP servers only (P4).
  • In Actions, only users with write access trigger runs and bots are rejected; each run gets a turn limit and the deny rules (P5).
  • curl and wget aren’t auto-approved, and for most fetches WebFetch gives Claude a separate model call’s answer about the page rather than the raw page.
  • Auto mode’s classifier blocks actions that look driven by hostile content; the sandbox’s network allowlist still holds if an injection gets past Claude (both Q1).
  • People review Claude’s changes before merging and report odd behavior with /feedback.
Security engineer · S5 S9
R3 · A surprise bill
  • On Teams the seat allowance is the default ceiling. Usage credits stay off until Q4, then run under organization, group or member spend limits.
  • CI runs on its own Console workspace with a spend limit, plus a turn limit, job timeout and concurrency limit (P5).
  • P1 baseline and monthly comparison (P6). For scale, the docs report about $13 per developer per active day across enterprise deployments, $150–250 a month, and under $30 per active day for 90% of users: a reference, not a forecast.
Platform lead with finance partner · S7 S9
R4 · Policy missing or bypassed on some machines
  • The docs call server-managed settings a client-side control, not a security boundary: on unmanaged devices a user can bypass them without admin rights, versions that predate them don’t fetch them, and a third-party provider variable or custom ANTHROPIC_BASE_URL skips the fetch.
  • Spot-check /status during P3; Q3 decides on MDM for the Macs.
Security engineer · S4 S13
R5 · One bad policy edit reaches everyone at once
  • Server-managed settings apply to the whole organization. Keep the policy JSON in a reviewed repo, validate each change with claude doctor on a test machine, then paste it into the console.
Platform lead · S10

Rollback

Each phase above ends with its own rollback line. These rules hold across all of them. S10

  • Undo in reverse. P4’s keys live inside P3’s policy, so clearing the policy removes both. P5 and P6 can be undone on their own.
  • Full stop. Taking Claude Code access off seats in the admin console stops interactive use; deleting the workflow files stops CI.
  • What lingers. Clients keep a cached copy of server-managed settings until their next successful fetch. A deleted GitHub secret leaves its API key valid until the key is deleted in the Console. Transcripts stay on laptops for up to 30 days by default. Approvals saved with “Yes, and don’t ask again” stay in each person’s .claude/settings.local.json.
