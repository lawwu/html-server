Claude Code permissions — three wireframe directions

Wireframes for a screen where someone reviews and edits their Claude Code permission rules. Every direction has to answer one question: what is Claude allowed to do in this project without asking, and where does each rule come from?

Same content in every direction

  • Project acme-app: a trusted folder, in Manual mode.
  • 16 rules in four settings files: Managed 4, Project local 2, Shared project 6, User 4. None from the command line.
  • Two rules don’t apply: a User allow for Bash(curl *) that a managed deny blocks, and a Project local allow for Bash(git push *) that a Shared project ask out-ranks.

How Claude Code combines rules

  • Rule lists from every settings file merge; no file replaces another’s list.
  • Deny is checked first, then ask, then allow. The first match decides, whichever file it’s in and however specific it is.
  • Nothing outside managed settings can lift a managed rule.
  • Anything no rule matches follows the permission mode.

What it tests

Whether people think of their rules as “my file versus the team’s file” first, and whether adding a rule inside the file it writes to removes the destination question.

Gains

  • Same model as /permissions: each rule beside the file it comes from.
  • “Add rule here” needs no destination picker.
  • Managed rules are fenced off as read-only in one block.

Costs

  • Files sit in precedence order, which suggests the top file wins. For permission rules it doesn’t.
  • Each conflict spans two groups (curl: Managed and User), so its explanation has to point across the page.
  • No single place answers “can Claude run git push?”

Pinned notes

  1. Without this line the order reads as “higher file overrides lower”. Lists merge, then deny → ask → allow decides.
  2. Project local sits above Shared project, yet its allow loses to the shared ask. Is a “Why?” disclosure enough, or should the row link to the rule that wins?
  3. Show an empty source like Command line, or hide sources with no rules?

What it tests

Whether people review by capability (“what can it do in the shell?”), and whether left-to-right lanes teach the deny → ask → allow order.

Gains

  • The git push conflict shows without reading: the ask and the struck-out allow are neighbours.
  • Each tool ends with what happens when no rule matches.
  • “Add Bash rule” names the tool up front.

Costs

  • Adding needs a destination choice, because the file is no longer the frame.
  • Sparse: 4 of 15 lanes are empty even with 16 rules.
  • Provenance is a tag; the file path is one legend away.

Pinned notes

  1. Tags replace the file path. Are “Shared project” and “Project local” clear without the path beside them?
  2. Lanes run left to right in evaluation order. Does that teach the order, or read as a pipeline a call flows through?
  3. MCP grows with every server: one group, or one per server?

What it tests

Whether outcome-first groups with plain-language labels answer the question faster than A or B, and whether nesting a losing rule under the rule that beats it explains conflicts.

Gains

  • The first group is the literal answer to the question.
  • Rules that don’t apply sit under the rule that beats them, with the reason.
  • “Anything else” ties the list to the permission mode.

Costs

  • Cleaning up one file means hunting through every group.
  • The single “Add rule” asks for type, rule and file every time.
  • Ordered by the question, not evaluation order, so the reasons have to teach deny → ask → allow.

Pinned notes

  1. Static example. A real lookup needs Claude Code’s own matcher (compound commands, wrappers), so building it is a product decision, not a wireframe one.
  2. Without a fixed file, the form defaults to Project local: only you, and where prompt approvals already save. Confirm.
  3. If the organization sets allowManagedPermissionRulesOnly, every user, project and local rule is ignored and new rules can’t be saved: one banner, or every row?

What collapses where

  • Outcome groups become accordions, and only “Runs without asking” starts open, because it is the question.
  • Each row keeps three lines: plain words, the rule, the source’s name. The file path moves to a row detail screen, not drawn.
  • The two rules that don’t apply leave the counts and sit behind one banner, each with its one-line reason.
  • “Add rule” becomes a bottom bar. Its sheet is the desktop form stacked: type, rule, then file.

The other two on a phone

  • A folds into five file accordions and loses nothing it had.
  • B stacks its lanes per tool, which breaks the side-by-side comparison that is its reason to exist.

Assumptions

  • A graphical surface: desktop app, IDE panel or web. In the terminal, /permissions already lists every rule with the settings file it comes from.
  • acme-app is trusted. Until a folder is trusted, allow rules in its .claude/settings.json don’t apply; that state needs its own design.
  • Manual mode throughout. In dontAsk mode an ask rule denies instead of asking, so every direction keeps the mode in its title bar.

Deferred to a mockup

  • Colour for deny, ask and allow; here they differ only by fill.
  • Icons for tools and settings files.
  • Type scale, row density and spacing.
  • Motion for opening rows, accordions and the form.
